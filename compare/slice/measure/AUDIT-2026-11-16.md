# Zubra audit, 2026-11-16

This compares Zubra 5.19.0 (the latest release) with Zubra `main` at 54b9978, which has 29 unreleased commits including the sync and list work from #317–#321. Everything was measured with the same slice, contract and `measure.mjs` as `RESULTS.md`, with the server pinned to one CPU.

- **Builds:** `zubra` (with `@zubra/sync`) and `zubra-stream` (server-sent events), each run on 5.19.0 and on `main`.
- **What came from `main`:** `@zubra/runtime`, `@zubra/server` and `@zubra/sync`.
- **What didn't:** the compiler stayed at 5.19.0, because `main`'s compiler is Rust built to WebAssembly and the Rust toolchain couldn't be downloaded here. That gap is what exposed the regression below.

Raw figures: `audit-2026-11-16-unfixed.json` (main as published) and `audit-2026-11-16.json` (main with a one-line local fix).

## 1. Regression on `main`: live updates break in production

Run as published, both `main` builds failed the contract (9 of 11, failing S6 and S8), and 12 of 12 menu and order updates never showed. The browser logged:

> The requested module '@zubra/runtime' does not provide an export named '$element'

In production, `@zubra/server` sends the one-file runtime `dist/bundled/zubra.js`. That file leaves out `$define` and `$element`, which `src/index.js` re-exports from `legacy.js`. Components compiled by 5.19.0 import `$element`, so they never start. Development mode isn't affected.

Adding the missing re-export to the bundle fixes it, and all 11 checks pass. Filed as journey-to-code-org/zubra#346 with `found-by: potomac`. It's the reverse of #324: newer server and runtime, older compiled output.

## What it means

- **Sync got smaller, as hoped.** With the minified sync build and webrtc.js loaded only when needed, the `zubra` build sends 20.1 KB instead of 27.5 KB, in 4 files instead of 5. Blocking time on a slow phone roughly halves (97 → 56 ms; 147 → 71 ms in the second run). That closes most of the gap with the stream build, but not all of it; #319, a smaller read-only connection, is still open.
- **The runtime change stays small.** Without the fallback, the stream build is about the same size (15.1 → 15.4 KB).
- **Old compiled output costs more on `main`.** The fallback works once #346 is fixed, but it adds `legacy.js` plus two or three more requests, and the menu's load event on a slow device goes from about 250 to about 330–360 ms. Recompiling with the matching compiler should avoid that, but couldn't be measured here.
- **Server throughput may have dropped.** In both runs, `main` served fewer menu pages per second: about 4–12% fewer for `zubra` and 20% fewer for `zubra-stream`. Absolute numbers moved about 10% between runs on this machine, but `main` was lower every time. The new per-page development checks in `@zubra/server` (#325, #327, #324) are the likely place to look; they may run in production too. That's a suspicion, not yet a finding, so nothing has been filed.
- **Live update speed is unchanged.** Menu and order updates still take about 7–10 ms, the same as before and as the web-component libraries.

## Developer-experience issues from the earlier log

- **Fixed on `main`:** #325 (a page finished by another page object), #329 (hydration mismatch location), #320 (a slot in two branches), #317 and #318 (sync size), #332 (docs).
- **Changes on `main`, issue still open:** #324 (a compiler newer than the runtime now gets a warning), #327 (an unknown sibling tag now gets a warning), #330 (a router load that throws now names the route and file), #331 (`cache: false` is now documented). These could probably be closed when 5.20 ships.
- **Still open, with no change seen on `main`:**
  - #300: the router renders a component twice when the layout and the page both import it. Potomac HQ still works around this.
  - #319: no smaller read-only sync connection.
  - #326: a prop set before the element is defined is lost.
  - #328: a sync collection the server won't let a page read looks the same as an empty one.
  - #333: no server starter, and the server, actions and router docs aren't together in one place (the new `create-zubra` starter page is a start).
  - #334: `zubra check` doesn't take a folder.
  - #335: an unknown prop points at line 1:1, and an unknown component suggests no name.

## Before calling 5.20 an upgrade

1. Fix #346, and add a test that runs older compiled output through the bundled runtime in production.
2. Re-run this audit with the compiler from the release. Then figures 1 and 2 above no longer need a caveat.
3. Check whether the per-page checks run in production. If they do, gate them to development, then re-run the load test.
